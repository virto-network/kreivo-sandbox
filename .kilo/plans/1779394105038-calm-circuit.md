# Forklift Migration Plan

## Goal

Replace the current `Chopsticks + @polkadot/api + node` sandbox stack with a `Forklift + polkadot-api` stack, using Bun for development/tooling where helpful while keeping the published library and CLI Node-compatible, and support:

- safe local forks of production/testnet chains for operational rehearsal
- fast sandbox bootstrapping for library/service/e2e tests
- relay + sibling parachain topologies for XCM scenarios
- continuous block production, manual branch control, reorg/finalization simulation, and pruning
- explicit teardown that really severs client/server connections
- an npm-consumable library and a thin CLI

## Current-State Findings

1. The current public library surface is centered on `ChopsticksClient`, `SandboxClient`, `Network`, `ChainIds`, and `RuntimeLogLevel`.
2. The runtime is tightly coupled to Chopsticks primitives: `setup`, `setupWithServer`, `ChopsticksProvider`, `connectVertical`, `connectParachains`, `setStorage`, `overrideWasm`, and `blockchain.newBlock()`.
3. The stack is also tightly coupled to `@polkadot/api`, including custom type registration and dynamic type construction.
4. The CLI is Node-only today and depends on `ts-node` and decorator-based `commander-ts`.
5. There are no repo tests covering sandbox lifecycle, topology wiring, upgrade flow, or CLI behavior.
6. The package is consumed through `npx`, so the published CLI cannot depend on Bun-only runtime APIs.

## Forklift Findings

1. `forklift.serve` is already a public `JsonRpcProvider`, so a `polkadot-api` provider does not need to be invented locally.
2. `forklift` supports `newBlock`, `changeBest`, `changeFinalized`, `setStorage`, `getStorageDiff`, `changeOptions`, and `destroy` programmatically.
3. Multi-chain XCM attachment is available through custom RPC methods: `forklift_xcm_attach_relay` and `forklift_xcm_attach_sibling`.
4. `forklift` does not publicly expose a first-class `wasm-override` feature like Chopsticks.
5. A bootstrap-time runtime override is still feasible by wrapping `wsSource` with a custom `Source` that overrides the `:code` key before `forklift(source)` initializes.
6. The built-in RPC surface does not expose `changeBest`, `changeFinalized`, `destroy`, or `getStorageDiff` remotely, so Kreivo will need custom RPC extensions if the CLI must drive those behaviors against a running sandbox.
7. `forklift`'s provider connection `disconnect()` is effectively a no-op, so Kreivo should own socket lifecycle explicitly in its WS server layer.
8. Upstream collaboration is available, so any cleanly generic improvement should be treated as a possible upstream PR rather than an automatic local-only patch.

## Recommended Direction

Treat this migration as a **major-version redesign** with these rules:

1. Keep the top-level product goals, but allow the CLI UX to change if that yields a better control surface.
2. Stop exporting engine-specific public classes like `ChopsticksClient`.
3. Move to engine-agnostic primitives built around `Forklift`, `JsonRpcProvider`, and a topology orchestrator.
4. Use Bun for local development, scripts, and tests where it improves ergonomics, but keep the shipped runtime code portable enough for Node-based tests and `npx @virto-network/kreivo-sandbox`.
5. Preserve support for runtime upgrade testing and runtime bootstrap overrides, but implement them through Forklift-native mechanisms instead of Chopsticks APIs.

## Target Architecture

### 1. Core Primitives

Define four main concepts.

- `ChainId` / `ChainProfile`
  - static identity and defaults for known chains
  - includes para id, default endpoints, and optional relay relationship metadata
- `EndpointPreset`
  - plain data + resolver helpers for `kusama`, `paseo`, and env overrides
  - replaces the current OO `Network` classes with a simpler endpoint library
- `SandboxChain`
  - one forked chain instance
  - owns the Forklift engine, provider, optional WS server, control RPC helpers, and teardown
- `Sandbox`
  - multi-chain topology orchestrator
  - owns relay/parachain/sibling attachment, port allocation, startup ordering, and cross-chain helpers

### 2. Public Library Surface

Expose a provider-first library API.

- `createSandboxChain(options)`
  - starts one forked chain
  - returns a `SandboxChain`
- `createSandbox(options)`
  - starts a topology containing Kreivo, optional relay, and optional siblings
  - returns a `Sandbox`
- `endpoints`
  - exports preset endpoint maps and resolvers
- `serve(chain, options)` or `chain.listen(options)`
  - exposes a local WS endpoint for tools that require an actual socket URL
- `chain.provider`
  - direct `JsonRpcProvider` for `createClient(chain.provider)`
- `chain.client()`
  - convenience helper returning a `polkadot-api` client bound to the in-memory provider
- `chain.rpc.*`
  - typed helpers over custom control RPC methods when the chain is served over WS

Recommended `SandboxChain` responsibilities:

- `provider`
- `forklift`
- `server` / `wsUrl` when listening
- `newBlock(opts)`
- `changeBest(hash)`
- `changeFinalized(hash)`
- `setStorageRaw(hash, changes)`
- `setStorageDecoded(hash, overrides)`
- `getStorageDiff(hash, baseHash?)`
- `destroy()`

Recommended `Sandbox` responsibilities:

- `chains`
- `get(name)`
- `initialize()` only if lazy startup is desired, otherwise start eagerly in factory
- `attachRelay(child, relay)`
- `attachSibling(a, b)`
- `runUpgrade()` or `upgrade.run(...)`
- `destroy()`

### 3. Kreivo-Specific Service Layer

Keep higher-level flows separate from the generic engine.

- `upgrade`
  - authorize + enact + verify runtime upgrade
  - support both bootstrap-time runtime override and real on-chain upgrade flow
- `storage`
  - raw and decoded storage override helpers using metadata builders
- `xcm`
  - attach relay and siblings, plus any Kreivo-specific XCM bootstrap helpers
- `accounts`
  - migrate community/sovereign account utilities away from `ApiPromise`

### 4. Control RPC Extensions

Add local RPC methods on top of Forklift with `rpcOverrides` so the CLI and remote test harnesses can drive advanced scenarios.

Recommended methods:

- `sandbox_newBlock`
  - wrapper over `forklift.newBlock` with explicit parent/type options
- `sandbox_changeBest`
- `sandbox_changeFinalized`
- `sandbox_getStorageDiff`
- `sandbox_destroy`
  - destroys the fork and closes all active sockets
- `sandbox_info`
  - returns chain name, para id, port, best hash, finalized hash, and runtime version

This is the missing piece that turns Forklift from a low-level engine into a functional sandbox control plane.

### 5. WS Server Ownership

Do not depend on Forklift's internal Node server helpers or the provider's no-op disconnect behavior.

Implement a local WS bridge with a shared connection manager and a Node-compatible default adapter. An optional Bun adapter can be added if it remains a thin wrapper over the same lifecycle layer.

The server layer must:

- upgrades HTTP to WS
- opens a Forklift provider connection per socket
- tracks all live sockets/connections
- closes all sockets during `destroy()`
- rejects new connections after shutdown begins

This directly addresses the requirement that the underlying client connection must actually die when requested.

### 6. Runtime Override Strategy

Support two different runtime paths.

- Bootstrap override
  - implement `withRuntimeOverride(source, wasm)` that wraps `wsSource` and returns overridden `:code` at startup
  - use this for the current `wasmOverrides` use case
- Real upgrade flow
  - keep a first-class upgrade helper that submits the runtime upgrade path against the sandboxed chain and verifies the runtime version bump

This avoids blocking on an upstream Forklift feature while still removing Chopsticks.

## Package and Tooling Changes

1. Replace `npm + package-lock + ts-node + node --loader` scripts with a Bun-driven development workflow.
2. Replace `commander-ts` decorators with a plain runtime parser, ideally `commander` or a similarly simple Node-compatible parser.
3. Remove direct dependencies on:
   - `@acala-network/chopsticks`
   - `@polkadot/api`
   - `@polkadot/wasm-crypto`
   - `ts-node`
4. Add direct dependencies on:
   - `@polkadot-api/forklift`
   - `polkadot-api`
   - `polkadot-api/ws`
   - `@polkadot-api/metadata-builders`
   - `yaml` only if config-file support is kept
5. Keep the package ESM-only.
6. Consider subpath exports such as:
   - `.` for the main library
   - `./endpoints` for the endpoint preset library
   - `./cli` only if programmatic CLI reuse is desired

## CLI Redesign

The CLI should be thin over the library, not a separate implementation.

Recommended scope for the first pass:

1. `kreivo-sandbox start`
   - start Kreivo with optional relay and siblings
   - print ports, ws URLs, runtime versions, and head/finalized info
   - make this the default command when no explicit subcommand is given
   - optionally expose MCP for the live instance via `--mcp`
2. `kreivo-sandbox account-ids`
   - preserve the existing utility behavior after migrating it to `polkadot-api`
3. `kreivo-sandbox block`
   - create blocks manually when running in manual mode
   - optionally branch from a parent hash
4. `kreivo-sandbox finalize`
   - change finalized head explicitly
5. `kreivo-sandbox best`
   - change best head explicitly to simulate reorgs
6. `kreivo-sandbox destroy`
   - kill a running sandbox and all client sockets

CLI recommendation:

- Keep the existing flags only where they still fit the new model.
- Prefer a clearer subcommand-based UX over strict flag-level compatibility.
- Add first-class controls for block mode, finalization mode, fork block, reorg/finalization actions, and config-file driven topologies.

## Implementation Phases

### Phase 1. Replace Runtime and Dependency Foundations

1. Convert scripts and local development flow to Bun.
2. Replace the decorator-based CLI stack.
3. Swap `@polkadot/api` and Chopsticks dependencies out of the core package.
4. Keep the initial export map small while the new API settles.
5. Preserve Node execution for the published CLI and runtime library paths.

### Phase 2. Build the Forklift Adapter Layer

1. Implement `createForkliftSource()` around `wsSource`.
2. Add `withRuntimeOverride()` source wrapper for bootstrap WASM replacement.
3. Wrap `forklift(source, options)` in an internal adapter that normalizes lifecycle, block controls, storage controls, and teardown.
4. Expose the raw `JsonRpcProvider` without forcing a WebSocket server.

### Phase 3. Add WS Serving and Custom RPC Controls

1. Implement the shared WS connection manager and a Node-compatible server adapter.
2. Track open sockets and provider connections.
3. Add custom RPC methods for best/finalized/diff/destroy/info.
4. Ensure `destroy()` closes server sockets, provider connections, and upstream source connections deterministically.
5. Add a Bun adapter only if it stays a thin compatibility layer over the same shared lifecycle code.

### Phase 4. Rebuild Topology Orchestration

1. Replace `SandboxClient` with a topology-oriented `Sandbox` abstraction.
2. Start chains from endpoint presets and requested roles.
3. Attach relay and siblings with `forklift_xcm_attach_relay` and `forklift_xcm_attach_sibling`.
4. Preserve deterministic default ports where useful, but make them configurable.

### Phase 5. Migrate Kreivo-Specific Services

1. Reimplement decoded storage override helpers using `@polkadot-api/metadata-builders`.
2. Rebuild the runtime upgrade helper on top of `polkadot-api` clients.
3. Migrate account-id utilities away from `ApiPromise`.
4. Move any ad hoc `kusama/*` scripts into reusable helpers, examples, or tests.

### Phase 6. Redesign Public Exports

1. Export the new provider-first API.
2. Export the endpoint preset library.
3. Do not preserve `SandboxClient` or `ChopsticksClient` compatibility shims unless a concrete downstream consumer requires them.
4. Keep stable chain ids and endpoint presets, but allow the rest of the library API to change.

### Phase 7. Rebuild the CLI on Top of the New Library

1. Implement `start` with current parity flags.
2. Add block/reorg/finalization/destroy commands.
3. Print richer chain info including both best and finalized heads.
4. Keep the CLI stateless except where it is controlling a running sandbox endpoint.

### Phase 8. Add Validation Coverage

1. Add unit tests for:
   - endpoint resolution
   - runtime override source wrapper
   - RPC override methods
   - teardown behavior
2. Add live integration smoke tests for:
   - single-chain startup
   - relay + sibling attachment
   - manual block creation and finalization changes
   - runtime upgrade flow
3. Keep live tests opt-in or env-gated if public RPC dependency would make CI flaky.

## Migration Risks and Mitigations

1. `polkadot-api` migration risk
   - Mitigation: keep the library provider-first so downstream consumers can use their own typed descriptors.
   - Mitigation: isolate Kreivo-specific typed logic inside helper modules instead of making it the public foundation.
2. Runtime override parity risk
   - Mitigation: ship the `Source` wrapper immediately rather than waiting on upstream Forklift changes.
3. Remote control surface gap
   - Mitigation: add custom RPC methods rather than forcing callers to run inside the same process.
4. Teardown correctness risk
   - Mitigation: own the WS bridge and close sockets explicitly.
5. CLI migration risk
   - Mitigation: switch to a clearer subcommand model and preserve only the workflows that matter.
6. Node compatibility risk
   - Mitigation: keep runtime code free of Bun-only APIs on the published path, and treat Bun as a tooling optimization rather than a hard runtime dependency.
7. Local divergence from Forklift risk
   - Mitigation: upstream generic fixes when they are broadly useful, especially around runtime override ergonomics, exported server helpers, or control RPC surface.

## Locked Decisions

1. Compatibility boundary
   - Treat this as a major-version API break.
   - Preserve workflows and endpoint identities, not the current class API.
2. Runtime support boundary
    - Keep Node-compatible published artifacts for both the library and CLI.
    - Use Bun for development/tooling where it helps, without making Bun a hard runtime requirement for consumers.

3. Accounts scope boundary
   - Remove community/sovereign account-id utilities from this package.
   - Treat them as a separate library concern, targeting a future package such as `@virto-network/community-utilities`.
   - This package should not keep a first-class `account-ids` CLI flow once the redesign lands.

4. Storage override input boundary
   - First-class storage overrides must support YAML input.
   - Support both single-chain YAML inputs and multi-chain YAML inputs in one file.
   - The override format should support decoded storage writes first, with raw-key escape hatches only if needed.

5. Governance emulation boundary
   - Add a governance outcome emulation flow on top of scheduler storage injection.
   - The flow must let the user select a sandbox chain, inspect available origins from runtime metadata, choose or paste an origin in structured object notation, provide call data, and pick the target execution block.
   - The implementation should prefer metadata-driven origin discovery over hardcoded origin enums.

6. Remote automation boundary
   - Add an HTTP-based MCP surface to expose control operations for live sandbox instances.
   - Treat MCP primarily as a debug console for a running sandbox, not as a separate standalone sandbox launcher.
   - Prefer exposing MCP from `start --mcp`, with optional stable registration ids, over a separate `mcp serve` lifecycle.
   - Prefer a Node-compatible Streamable HTTP transport so CLI and signing workflows can integrate without shelling into the sandbox process directly.

7. Local replay diagnostics boundary
   - Add a local block replay diagnostic flow for sandboxed chains.
   - The initial scope is local block execution replay only, not XCM-specific dry-run or cross-chain message replay.
   - Replay should execute block phases against a shadow overlay without mutating the sandbox head by default.
   - Replay output should prioritize runtime logs, per-phase storage diff, and per-extrinsic results to debug locally silent failures.

## Proposed Execution Order

1. Land the Bun/tooling migration and dependency swap.
2. Land the Forklift chain adapter and runtime override source wrapper.
3. Land WS serving plus custom sandbox RPC methods.
4. Land the multi-chain topology orchestrator.
5. Land Kreivo-specific storage and upgrade utilities, explicitly excluding the community account-id flow from this package.
6. Land YAML-driven storage override ingestion and application.
7. Land the governance outcome emulation flow, including metadata-driven origin discovery and interactive selection.
8. Land the CLI rewrite on top of the new library and governance/storage flows.
9. Land the HTTP-based MCP server on top of the same library primitives.
10. Land local block replay diagnostics for replaying a block against a chosen parent state without mutating the chain.
11. Upstream any generic Forklift improvements discovered during implementation.
12. Land validation coverage and remove the old Chopsticks code paths.

## Additional Scope Addendum

### A. Accounts Extraction

The redesigned sandbox should not own long-term community account derivation utilities. During the migration:

1. Remove public exports and CLI commands that present account-id derivation as part of this package.
2. If temporary compatibility code remains during the transition, keep it isolated and clearly marked for extraction.
3. Align naming and docs with the intended external package boundary: `@virto-network/community-utilities`.

### B. YAML Storage Overrides

Add a storage override ingestion layer with these properties:

1. Accept a YAML file that targets one chain:
   - identifies `chain`
   - defines decoded storage changes, and optionally raw storage changes
2. Accept a YAML file that targets multiple chains:
   - identifies `chains.<chainId>` blocks
   - allows the same decoded/raw override structure per chain
3. Provide a library helper to parse and validate the YAML into normalized override operations.
4. Add CLI flags so sandbox startup can apply one or more YAML override files before higher-level flows run.

### C. Governance Outcome Emulation

Add a governance-oriented service and CLI/TUI flow that:

1. Discovers sandbox chains from sandbox state or a generated manifest.
2. Lets the operator choose a chain interactively.
3. Inspects runtime metadata to discover the exact scheduler origin type.
4. Presents the available origin variants in a TUI and also accepts a pasted structured object notation payload.
5. Accepts call data and target block number.
6. Injects the appropriate scheduler agenda storage so the chosen origin executes the chosen call at the chosen block.

### D. HTTP MCP Surface

Add an MCP server layer with these first-pass goals:

1. Use Node-compatible Streamable HTTP transport.
2. Expose sandbox lifecycle/control operations as MCP tools rather than inventing a separate automation-specific API.
3. Keep sandbox instances in an in-memory registry keyed by sandbox id.
4. Reuse the same library primitives used by the CLI so the MCP surface stays thin.
